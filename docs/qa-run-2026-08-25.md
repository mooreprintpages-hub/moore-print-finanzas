## Validaciones aprobadas

### RLS estructural

Todas las tablas públicas inspeccionadas tienen RLS activado y al menos una policy. No se detectaron tablas públicas del modelo operativo con RLS deshabilitado.

### Propietario

La membresía activa está ligada al rol `Propietario` y el rol tiene 33 permisos permitidos.

Simulando la sesión Auth del propietario bajo el rol PostgreSQL `authenticated`:

- Puede ver el negocio.
- Puede crear un área ligada a la sucursal existente.
- La escritura de prueba fue revertida con `ROLLBACK` y no dejó datos permanentes.

### Usuario externo / sin membresía

Simulando un UUID sin membresía bajo el rol PostgreSQL `authenticated`:

- Ve 0 negocios.
- Ve 0 clientes.
- Intentar insertar un área para Moore Print falla con `new row violates row-level security policy for table "areas"`.

### Rol limitado sin permisos

Se creó temporalmente un rol sin permisos, se asignó al miembro activo dentro de una transacción y se simuló su sesión `authenticated`. Todas las siguientes escrituras fueron bloqueadas por RLS:

- Administración / áreas: falta `users.manage`.
- Finanzas / presupuestos: falta `finance.manage`.
- Ajustes de inventario: falta `inventory.adjust`.
- Compras: falta `purchases.create`.
- Workflows de producción: falta `workflows.manage`.
- Cotizaciones: falta `quotes.create`.

La transacción terminó con `ROLLBACK`, por lo que la cuenta conservó su rol `Propietario` sin cambios permanentes.

### Compra, recepción parcial e inventario

Durante QA se encontraron y corrigieron dos incompatibilidades reales del backend:

1. El trigger de recepción usa `inventory_movements.movement_type = 'purchase_receipt'`, pero el CHECK original no aceptaba ese valor.
2. El registro de costo usa `material_costs.source = 'purchase_receipt'`, pero el CHECK original tampoco lo aceptaba.

Después de corregir ambos CHECKs, una compra de 10 unidades a $20.00 validó:

- Total de compra: $200.00.
- Recepción parcial: 4/10.
- Compra e ítem: `partially_received`.
- Lote creado.
- Inventario físico/disponible: 4/4.
- Costo de material registrado desde la recepción.

### Reservas y consumo de inventario

Se detectó que la UI sólo marcaba una reserva como `consumed` sin crear el movimiento de consumo, lo que devolvía material usado a disponibilidad.

Corrección aplicada mediante `public.consume_inventory_reservation(uuid)` con `SECURITY INVOKER`, ejecutable sólo por usuario autenticado y sujeto a las policies existentes de `inventory.adjust`.

Validación:

- Inicial: 4 físicas, 2 reservadas, 2 disponibles.
- Tras consumir: 2 físicas, 0 reservadas, 2 disponibles.
- Reserva: `consumed`.
- Movimiento `consumption`: exactamente 1.

El frontend también fue corregido para usar `orders.folio` en lugar de la columna inexistente `orders.order_number` dentro de Inventario avanzado. Cambio fusionado en PR #39.

- Consumo de inventario: 2 unidades físicas restantes.

### Contratos frontend ↔ Supabase

QA encontró dos referencias adicionales a la columna inexistente `orders.order_number`:

- `OperationsPage.tsx`.

Ambas fueron corregidas para usar `orders.folio`, y el cambio pasó TypeScript + Vite y quedó fusionado en PR #40.

## Seguridad

Supabase Security Advisor reportó una advertencia: `Leaked Password Protection Disabled`. No es una falla de RLS; corresponde a una opción de seguridad de Supabase Auth que conviene activar antes de producción definitiva.

Performance Advisor reportó principalmente índices aún no utilizados, esperable por el bajo volumen de datos. También señaló un FK de `budgets.created_by` sin índice y políticas permisivas múltiples para UPDATE en `approval_requests`; son optimizaciones pendientes, no fallas funcionales bloqueantes.
